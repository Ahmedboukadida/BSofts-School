# Database Provisioning & Multi-Tenancy Control: Current State and What It Would Take

Prepared 2026-07-29, based on two full code audits across erp-back's four active solutions (Structure, Subscription, Authentification, Vente) and erp-front. No database network access from this environment, so every finding below comes from reading the actual code and config, not a live query — cited by file so you can verify directly.

## 1. The headline finding

AxiaERP has no per-company database isolation today, in any functional sense. All companies share exactly one Structure database, one Subscription database, one Identitydb, and one Ventes database — four total, all on the same Postgres host (`172.0.1.131`). Every field that looks like it supports per-company hosting is either dead or cosmetic: `Subscription.CompanyDbUrl` is written but never read anywhere to route a connection; the "Cloud vs Local" hosting choice in the approval wizard is frontend-only React state that never becomes a real backend concept — the backend's derived version of it is buried in a JSON blob (`CompanyJsonPf`) that no code anywhere ever decodes. Tenant isolation today is entirely row-level: every per-company table depends on `IdSociete`/`CompanyId` being filtered correctly in every individual query, sourced from a JWT claim (`StructureAPI/Services/CurrentUserService.cs`) — there is no systemic enforcement (no EF global query filter keyed on company), which is exactly why the scoping bugs found earlier in this project exist at all (`SouchesClient` has no company column whatsoever; `Devise.DevIsBase` isn't filtered by company anywhere that reads it).

Each of the four backend APIs wires exactly one static connection string at startup and never revisits it per request — confirmed in `StructureAPI/Program.cs`, `SubscriptionAPI/Program.cs` (which opens three separate DbContexts — Subscription, Identitydb, and Structure — all in-process), `AuthentificationInfrastructure/DependencyInjection.cs`, and `VenteAPI/Program.cs`. `SubscriptionRequests/Approve` — the one place you'd expect provisioning to happen — makes 16 in-process EF writes across those three databases and never executes DDL or creates anything (`SubscriptionApplication/Features/SubscriptionRequestFeatures.cs`). Nothing in the repository issues `CREATE DATABASE`, `CREATE SCHEMA`, or anything resembling infrastructure provisioning — no such SQL, no Docker Compose file, no shell scripts exist anywhere in either repo.

## 2. Security issues found along the way — worth fixing regardless of anything else in this report

These aren't architecture gaps so much as live exposure, and none of them depend on deciding anything about the bigger provisioning question, so I'd treat this section as independent and first:

- The JWT signing secret is still the literal placeholder string `CHANGE_ME_SUPER_SECRET_KEY_MIN_32_CHARACTERS_LONG_PLEASE` — identical across `StructureAPI`, `AuthentificationAPI`, and `VenteAPI`'s `appsettings.json`. If any deployment of this config is reachable outside your own machine, this needs to become a real, unique, rotated secret before anything else here.
- `AuthentificationAPI/appsettings.json` ships a hardcoded seed admin credential (`admin@authservice.local` / `Admin@123456!`).
- The per-company `SecretKey` meant to protect a company's JSON profile defaults to `null` and silently falls back to one hardcoded literal, `"DefaultSecretKey"`, shared by every company that doesn't set one (`SubscriptionRequestFeatures.cs`). The function that's supposed to use it, `CryptJsonProfile`, doesn't actually take the key into account — it's reversible Base64 encoding, not encryption.
- The database password (`Demo123*`) and host are hardcoded not only in every `appsettings.json` but as literal fallback strings directly in C# source in two places (`StructureInfrastructure/Persistence/StructureDbContext.Fallback.cs`, `SubscriptionAPI/Program.cs`), so fixing config alone wouldn't fully remove them.
- `VenteAPI`'s CORS policy is hardcoded in `Program.cs` — including a literal placeholder domain, `https://votre-domaine-frontend.com` — and ignores a `Cors:AllowedOrigins` section that already exists, unused, in its own `appsettings.json`.

One thing I need from you before treating this section's urgency correctly: is `172.0.1.131` / `Demo123*` / this JWT secret specifically a disposable dev environment, or does this configuration (or something derived from it) travel toward a real deployment?

## 3. Why "just make it dynamic" is a bigger project than it sounds

Structure and Subscription have no EF Core Migrations — schema changes are 5 small hand-written patch scripts total (`StructureInfrastructure/Persistence/manual_sql/*.sql` ×3, `SubscriptionInfrastructure/.../manual_sql/*.sql` ×1, `AuthentificationInfrastructure/.../manual_sql/*.sql` ×1), and not one of them contains a single `CREATE TABLE` — they're all `ALTER TABLE`/`CREATE INDEX`/backfill statements that presuppose a schema that already exists. The actual baseline — the full table set a brand-new company database would need — isn't captured anywhere in either repository. The one database-first EF model that could theoretically stand in for a baseline, `StructureDbContext.cs`, has already drifted from the live schema: it's missing a partial unique index that one of the patch scripts added, so scaffolding a fresh database from it today would produce an incomplete result. Standing up a new company's database right now would mean either restoring a copy of an existing live database or hand-deriving DDL from a model that's already known to be wrong in at least one place.

Separately, `VenteAPI` is architecturally different from the other three: it reaches Structure over HTTP rather than sharing an in-process DbContext the way `SubscriptionAPI` currently reaches Subscription, Identitydb, and Structure directly. Provisioning "a company's database" is really up to four separate operations reached two different ways, not one.

## 4. The fork this depends on — I don't think this is mine to decide

**A — one shared database per solution, with isolation actually enforced.** Keep today's shape, but close the gap that lets bugs like `SouchesClient` or `Devise.DevIsBase` happen at all: add real EF global query filters keyed on company id, so isolation is enforced by the framework by default instead of depending on every query remembering to filter correctly. Substantially less work — no provisioning service, no baseline-schema project. Company data stays logically, not physically, separated.

**B — a real separate database per company.** This is what `CompanyDbUrl` and the hosting-choice UI appear to have been building toward: true physical isolation, and the ability to put a specific company on its own infrastructure. Much bigger build — someone first has to create the missing baseline-schema artifact, then an actual provisioning service (something that can run `CREATE DATABASE`, apply the baseline, generate real per-company credentials, and register the result somewhere the running application actually reads at connection time — none of which exists today), and the approval wizard's "Cloud vs Local" step needs to become a real trigger for that instead of a form that stores a string nobody reads.

I'd rather ask than guess here, because the honest cost gap between A and B is large — A closes a real but bounded gap in the current design; B is a new subsystem. If you tell me what "full control" means day to day — mainly confidence that one company can never see another's data, or specifically the ability to host an individual company on separate infrastructure — that tells me which one actually solves your problem.

## 5. What the Subscription solution would need to actually own this

Right now Subscription's approval flow is a bookkeeper, not an actor — it writes rows into databases it already has open, and never creates anything. Under A, "controlling the whole thing" means the approval flow becomes the place that guarantees a new company's rows get correct scoping from day one, and a natural home for running `axia-scoping-audit` for real, on a schedule, rather than as a one-off manual check. Under B, it means the approval flow needs real provisioning authority: create a database, apply the baseline schema, generate and store a real per-company credential (not today's shared fallback), and write it somewhere the application actually reads per request — which also means building the dynamic connection-resolution mechanism that doesn't exist anywhere today (all four APIs wire one static connection string at startup and never look again).

## 8. Decided direction: hybrid tenancy

Both, tiered, rather than either/or — and this actually resolves a loose end from section 1 rather than adding a new idea on top: `CompanyDbUrl` being nullable, defaulting to null unless an operator explicitly typed a `DbHost` during approval, already reads exactly like a switch nobody finished wiring — null meant to mean "pooled," a real value meant to mean "dedicated." The hybrid model just finishes that thought instead of replacing it:

**Tier 1 (default, every company starts here) — pooled, with isolation actually enforced.** Everyone lives in the existing shared Structure/Ventes databases, but with real EF global query filters keyed on company id, closing the SouchesClient/Devise class of gap for good instead of depending on every query remembering to filter correctly. This is section 4's option A, and it ships for 100% of companies regardless of who ever moves to Tier 2.

**Tier 2 (opt-in, per company) — dedicated database.** A specific company gets its own Structure database (and, if their sales-document volume or isolation needs justify it, their own Ventes database too), physically separate, potentially on separate infrastructure. This is section 4's option B, built as an upgrade path rather than the default for everyone.

**One clarification that matters once you're building both**: Identitydb and the Subscription database itself should almost certainly stay centralized regardless of tier. They're our platform's records — who can log in, which company they belong to, what they're subscribed to — not the company's own operational data. The application needs a single, always-reachable place to answer "which database does this logged-in user's company use" before it can even route them anywhere; if Identitydb itself were also split per company, nothing would know where to look first. So "dynamic" really only needs to apply to Structure and Ventes connections — Subscription and Identitydb keep working exactly as they do today, for every company, in both tiers.

Still open, and this one's a product decision rather than a technical one: what actually moves a company from Tier 1 to Tier 2 — a Pack-level attribute (e.g. an "Enterprise" pack implies dedicated hosting automatically), a manual decision your team makes per customer, or something a customer can request/self-serve? Tracked as T15 below; worth deciding before the approval-wizard UI work (T14) is finalized, though the backend provisioning capability (T10-T13) doesn't depend on the answer.
