## Notes from the third review pass

Independently verified against the actual code (not just prior passes' narrative) before making the corrections above — full evidence and file:line citations in `PROVISIONING_CONTROL_REPORT.md` section 11.

1. **T9a was under-scoped, and one of its two named bugs was mis-targeted.** `VenteInfrastructure/Repositories/` has six document repositories with the identical unscoped-by-id shape, not three: Facture, BonCommande, Devis, BonLivraison, BonRetour, FactureAvoir, all confirmed by direct read. The last three (not previously named) carry the same "mutates the cross-fetched source record" severity already flagged for Facture's conversions — e.g. `BonCommandeRepository.ConvertFromDevisAsync` unscoped-fetches and mutates a `Devis`; `FactureAvoirRepository.ConvertFromBonRetourAsync` unscoped-fetches and mutates a `BonRetour` (sets `IsConverted`/`IsArchived`/`NumeroFacture`/`DateFa`). Separately, `DeviseTauxRefreshService` — the "currency-refresh job" the second bug was attributed to — is not registered anywhere (`grep -rn "AddHostedService"` across the entirety of erp-back returns zero results): it is dead/dormant code, not a live bug. The real, live, wired, HTTP-reachable equivalent is `StructureInfrastructure/Repositories/Devises/DeviseRepository.cs`: `UnsetOtherBaseCurrenciesAsync` (called from `CreateAsync`/`UpdateAsync`) unsets `DevIsBase` on every other company's currency with no company filter at all — a cross-tenant **write/corruption**, not just a read leak — and `RefreshTauxAsync`/`ConvertAsync` both perform the same unscoped "pick any company's base currency" lookup. `Devise`'s own `GetByIdAsync`/`UpdateAsync`/`DeleteAsync` share the same bare-`Id`-no-company-check pattern as every other repository in this family. T9a's row above has been corrected accordingly; `DeviseTauxRefreshService` itself still needs a deliberate decision (fix it before ever wiring it up, or delete it) but it is not urgent the way everything else in T9a is.

2. **`StructureDbContext.cs` (1,153 lines) is a three-way collision, not two.** Confirmed by direct read: `Client`, `Company`, and the existing soft-delete `HasQueryFilter` block (`Company`/`CompaniesSetting`/`CompaniesSettingsKeysValue`/`CompaniesContact`/`CompaniesAddress`/`Country`/`State`/`Municipality`) are all configured in this one file. T6b (entity/DbContext mapping updates) edits it exactly as much as T7a and T10 do. The dependency chain already serializes T6b before T7a safely (T7a depends on 70), but T6b and T10 had no dependency relationship in either direction and were previously free to run fully concurrently on the same file with no warning at all. Both affected rows now name all three tasks. (`VenteInfrastructure/Persistence/VenteDbContext.cs` is a separate, 254-line file with zero existing query filters — T7b does not participate in this collision, confirmed by direct read.)

3. **T9b's closure check covered only half the scoping fixes in this plan.** As originally written it re-ran `axia-scoping-audit` only after T7a/T7b shipped, never re-checking T6 (`SouchesClient`) or T9a (the IDOR fixes) — both just as much a part of "is this properly isolated per company" as the global filters. Added 54 and 73 to its dependencies.

4. **T14 was missing a real dependency on T15**, carrying it only as a parenthetical ("should also wait on 63") instead of an entry in the `Depends on` column a task tracker would actually enforce. Promoted to a first-class dependency.

5. **T1 and T5b now both write to a JWT-secret config value, and neither says so.** T1 was scoped against three files (`StructureAPI`/`AuthentificationAPI`/`VenteAPI`'s `appsettings.json`) before T5b existed. T5b adds a fourth: confirmed `SubscriptionAPI/appsettings.json` currently has no `JwtSettings` section at all, so T5b's implementer creates one from scratch. Whichever of T1/T5b lands second should reconcile the secret value across all four files, not three. This is an implementer note, not a hard blocking dependency — either order produces a correct result as long as T5b's implementer copies the live value rather than the placeholder string frozen in this document. (Issuer/Audience needed for T5b — confirmed identical across all three existing APIs: `Issuer = "AuthService"`, `Audience = "AuthServiceClients"`.)

6. **T7a/T8 needed an explicit non-HTTP-context acceptance criterion**, not just a sequencing dependency. T8 already correctly gates T7a/T7b (both depend on 56), and its description already names two non-request code paths to audit — the background rate-refresh job and Subscription's in-process Structure writes — but neither the task descriptions nor T7a's scope said what T8 actually has to decide for either one. Two distinct flavors of the same underlying problem: (a) a `BackgroundService` (like the dormant `DeviseTauxRefreshService`, or any future one) has no `HttpContext`/JWT claim at all for a company-scoped filter to read "current company" from; (b) `SubscriptionRequestFeatures.ApproveCoreAsync`'s in-process writes into `StructureDbContext` *do* run inside an HTTP request (Subscription's own `Approve` endpoint), but that request's JWT belongs to platform staff approving the request, not to the brand-new company whose very first rows are being written — so "read current company from the caller's claim" is the wrong answer there too, just for a different reason. Left unstated, the easiest failure mode is a global filter that silently returns zero rows (or throws) for both cases the moment it ships — a materially worse regression than the bug T7a/T7b are fixing. Both rows now state this as a required deliverable of T8 (covering both cases explicitly) and an acceptance criterion of T7a, not an implicit assumption.
